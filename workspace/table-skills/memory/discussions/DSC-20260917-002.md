# Discussion

## Starting Point

讨论是否以及如何将“网页替身”的保留思路锻造成一个可安装的 Portable Skill。

## User View

用户认可其设计参考价值，并明确要求按实验性 `TEST` 方案锻造；当前版本不实测 Astra 模型。

## Challenges

- 原方案包含结果外包、MCP 服务、模型后端桥接和原生子任务等不同数据流，第一版若全部覆盖会模糊能力边界。
- “流程可运行”“上下文隔离”“自动化可靠”和“实际省 token”是不同结论。
- 网页对话的自动创建、发送和回收取决于宿主接口，不能由 Skill 文本凭空提供。
- 外部结果仍需核验；协调与重新采用结果的成本可能抵消收益。

## What Changed

候选 Skill 从泛化的“网页替身／省 token”收窄为“可核验的网页任务外包”：选择可独立的重任务，生成最小自包含任务包，经明确授权后提交，记录唯一任务身份，回收并核验紧凑结果。其他后端路线不纳入第一版。

## Agreement

- 第一版采用快速聊天或网页聊天的半自动入口，并在宿主缺少可靠接口时提供手动降级。
- 默认准备任务包不等于授权外部提交；发送仍需用户明确要求或清楚授权。
- 不保证降低 token，测试时从准备到核验采用计算完整成本。
- 当前版本不调用、不测试 Astra，也不以 Astra 作为基线；历史结果只作为来源背景。
- 实验结果必须限定到实际测试的模型、宿主、路线和日期。

## Unresolved

- 当前宿主能否稳定创建全新快速聊天并自动回收结果，需要实际使用时探测。
- 本版本在当前可用模型上的 token、延迟、失败率和人工介入成本尚无实测数据。

## Decision

`TEST`

已获用户明确确认：“按此方案锻造”。据此创建实验性的 `web-task-stand-in` Portable Skill。
