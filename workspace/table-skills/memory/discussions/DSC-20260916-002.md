# Discussion

## Starting Point

补充逆向阅读仓库的实际实现，讨论“压缩后交接”是否应作为一条自动串联链路。

## Source-grounded Finding

仓库本身采用“压缩检查点 → 提醒／保存 → 经明确授权后完整交接”的保守链路。其可迁移核心是最小事实包、状态证据、唯一接手任务、只读核验和结果未知时先查询；它没有把每次压缩自动升级为新任务。

## User View

用户明确表示：应当先压缩，压缩完成后直接进行交接，不需要用户再次确认。这里的意图是把压缩作为交接的自动触发，而不是把压缩与交接设计成两个需要分别批准的动作。

## Analysis

这构成对来源实现的适配，而不是对来源行为的逐字复制。自动化门槛从“用户确认完整交接”前移为“压缩完成”；安全性仍需由交接内部的回读校验、唯一任务、只读核验和修改权转移来提供。

## Decision

`ADAPT`

### Decision scope

采用“压缩产出交接材料并进入交接”的总体方向，但分阶段实现：第一版保持不自动触发，由用户或任务显式调用并完成验证；待核心交接 Skill 在实际使用中证明可靠后，再考虑用 Hook 触发。此阶段不自动采纳仓库的具体 Hook、阈值、任务 API 或网页替身实现。

## Unresolved

- 未来 Hook 触发是每次自动压缩，还是达到仓库所说的安全检查点／阶段条件，留待第一版使用证据决定。
- 接手方只读核验失败时，是否暂停自动转移修改权并回到源任务？
- 当前宿主缺少真实任务标识或创建接口时，自动交接应停在保存材料，还是生成可复制的手动入口？

## Follow-up Decision

用户确认先实现非自动交接版本，再以实际使用效果决定是否增加 Hook 触发。该决定保留了自动化方向，但将触发机制与核心交接逻辑解耦。
