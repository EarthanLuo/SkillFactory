# Evolution

## Trigger

第二次真实替身测试证明研究子 Agent 能返回紧凑结论，但运行期间的正文轮询重复带回上一轮长答案，使主会话上下文成本大幅增加。用户在看到测试结论后明确要求“修订”。

## Problem

旧 Skill 要求跟踪状态和限定读取，却没有禁止用会返回消息正文的接口轮询，也没有说明预览、旧轮次和封装重复可能绕过单条消息限制。回传预算按中文字符描述时也未覆盖链接等完整载荷。

## Previous Behavior

提交后可以通过读取对话检查是否完成；完成后再请求最新一轮并设置字符上限。该做法在 ChatGPT 对话仍运行时可能反复返回旧答案，并把原始对话封装直接带入主会话。

## New Behavior

- 等待与正文回收成为两个独立阶段。
- 优先使用不返回正文的状态操作；若只能读取对话，则在宿主侧只暴露状态和最新轮次标识，丢弃预览与消息正文。
- 禁止使用正文读取进行高频轮询；仍在运行时必须退避。
- 完成后只读取一次，选择提交后产生且任务 ID 匹配的最新 assistant 回答，不回传原始对话封装。
- 明确 `turnLimit` 和单项字符上限不是 token 安全保证。
- 回传预算覆盖标题、Markdown、引用和 URL 等完整载荷。
- 实验评估单独记录状态探测载荷与最终回收载荷，并将意外旧内容计入主会话成本。

## Reason

本次主要浪费发生在等待协议，而非替身研究本身。只有阻断旧正文在轮询阶段进入协调任务，紧凑决策包才可能转化为实际上下文节省。

## Alternatives Considered

- 只进一步缩短最终答案：未采用为唯一修复，因为无法阻止等待阶段回灌旧内容。
- 持续快速读取但设置更小的单项限制：未采用，因为宿主可能在受限消息之外继续返回预览或重复封装。
- 完全不跟踪任务：未采用，因为会降低自动化可靠性和重复发送防护。

## User Confirmation

用户在查看第二次实测结果和拟议方向后明确回复：“修订”。
