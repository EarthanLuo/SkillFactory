# Evolution

## Trigger

用户确认当前仍由主会话逐次轮询聊天状态，并明确要求改成“宿主侧等待脚本”。

## Problem

旧流程虽然过滤了探测正文，但主会话仍负责等待、读取状态、判断是否再次探测。桌面同步延迟通常造成多次工具往返。

## Previous Behavior

主会话先等待，再调用一次状态探测；若新回合尚未同步，则主会话再次等待和探测。完成后另行回收正文。

## New Behavior

新增 `scripts/host_wait.mjs`。桌面宿主向它注入原生 `readThread` 操作，在一个有界宿主调用内低频检查状态。中间响应不输出给主会话；发现基线之后、带任务 ID 的已完成助手回复时，直接清理并返回一次结果。默认 55 秒超时，只返回一个 `pending`，不重发任务。直接主会话探测降为宿主不支持组合等待时的回退路径。

## Reason

把等待调度和轮询响应留在宿主侧，可减少主会话工具往返和状态元数据，同时维持基线回合、任务 ID、引用清理和单次回收约束。

## Alternatives Considered

普通 Python 脚本无法直接访问桌面原生对话工具；无限后台轮询会引入不可控生命周期；把每次探测结果继续返回主会话不能解决问题。因此采用依赖注入的有界宿主集成脚本。

## User Confirmation

用户明确要求：“改成‘宿主侧等待脚本’”。
