# Evolution

## Trigger

用户理解 API Conversation 与桌面聊天的区别后，明确要求 Skill 引导用户先创建聊天会话，再把它告诉主会话。

## Problem

旧 Skill 在宿主缺少普通 ChatGPT 聊天创建接口时，没有完整的首次启动引导，容易停在“无法自动创建”或误选 Codex、Work、API Conversation。

## Previous Behavior

优先自动创建快速聊天，否则尝试选择现有聊天；两者都不可用时只提供手工任务包和回收说明。

## New Behavior

当没有目标聊天且宿主不能原生创建普通 ChatGPT 聊天时，Skill 暂停提交，指导用户在桌面应用中创建 ChatGPT Chat/Quick Chat，并通过会话引用、链接、标识符或唯一精确标题交回主会话。主会话验证身份后，将执行路线记录为 `user-created ChatGPT chat` 再继续。明确排除 Codex 任务、ChatGPT Work 任务和 API Conversation。

## Reason

这条人工启动路径利用已经验证可用的现有聊天操作能力，同时避免依赖不可靠的 UI 自动化或混淆不同会话类型。

## Alternatives Considered

自动点击桌面 UI 的可靠性较低；API Conversation 不会创建可见桌面聊天；静默复用任意已有聊天会污染上下文。因此采用用户创建、主会话验证的显式交接。

## User Confirmation

用户明确要求：“给 skill 里增加一个引导，告诉用户先去创建一个聊天会话，然后告诉主会话”。
