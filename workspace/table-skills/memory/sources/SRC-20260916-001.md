## Relevant Content

### Source claims

- README 将仓库定位为日常使用中的 AI Skills 与实验思路集合，当前维护“项目交接”；“网页替身”旧版实现已弃用，仅保留设计思路。
- 项目交接的目标是保存有效进度和决定，让下一次对话能够接续；重点保存目标、有效决定、关键文件、真实进度和下一步，而不是整段复制聊天记录。
- 仓库明确区分提醒、保存、完整交接、恢复／查看等入口；普通“继续”不等于同意新建任务。
- 完整交接被拆为收拢与确认去向、保存并校验、创建接手任务、登记并确认接手条件、发出继续指令并交出修改权、验证接续并打开。
- 记录应区分已确认、Agent 建议／自行选择、未决；区分已完成、进行中、未做、未验证；“已创建／已派发，接续待验证”不能写成“交接完成”。
- 失败恢复要求同一次交接只创建一个接手任务；结果不明时先查询，不盲目重发；核验未完成时不转交业务修改权。
- 可选 Hook 只辅助记录压缩检查点和最终文本核验，不能独立判断业务阶段，也不能证明用户已经看到提醒。
- README 对网页替身的实测结论带有模型范围：省 token 不理想的问题发生在 Astar 模型上，不能据此推断网页替身在所有模型或宿主中都无效；快速聊天可作为半自动入口，自动创建全新快速聊天仍缺少正式接口。

## Implementation Review

本次补充读取了 `project-handoff/SKILL.md`、`references/handoff.md` 与 `references/compaction-reminder.md`。实现上的关键做法是：把自动压缩计数与业务交接材料分开；只在宿主提供真实压缩事件和任务标识时评估检查点；压缩提醒、仅保存、完整交接、恢复／查看分别作为不同入口；完整交接时先保存并回读校验，再创建唯一接手任务，让接手方只读核验，登记真实任务编号后才发送继续指令并转移修改权；创建或发送结果不明时先查状态，不盲目重试。Hook 只负责计数、提醒和最终文本核验，不新建业务任务、不替代业务阶段判断或用户授权。

该实现的原始授权门槛仍然是“完整交接需用户明确要求或确认具体提议”。因此，它提供的是“压缩结果可直接成为交接材料”的机制，但并未实现“每次压缩后自动交接”；后者属于基于该实现思路的用户侧适配，而非仓库已验证的行为。
