# Feedback

## Skill Used

`web-task-stand-in`

## Situation

在 GPT/Codex 桌面应用中复用“重任务测试”聊天，将一项检索并比较 10 篇动态场景 3D Gaussian Splatting 论文的任务交给聊天替身，并测量协调主会话实际接收的载荷与账户用量窗口变化。不测试 Astra。

## What Happened

提交前，Codex 账户五小时窗口显示已用 43%，周窗口 37%。替身完成首稿后，工具内部过滤只向主会话暴露状态与长度元数据，没有暴露旧对话、原始响应包装或 3,560 字符的超预算首稿。随后在同一聊天请求压缩，最终回收 2,866 字符、4 个链接、启发式估算约 1,009 token 的未截断回复。结束后五小时窗口显示已用 45%，周窗口仍为 37%。百分比窗口无法给出此次任务的精确 token 消耗，也混合了协调会话本身的操作成本。

第一次结果提取未匹配成功，因为桌面返回把助手正文放在 `turn.items[].type = agentMessage` 的 `text` 字段，而临时筛选器仅通过字段路径中的 `assistant`、`agent`、`response` 或 `output` 判断角色；路径 `items[1].text` 本身没有角色词。元数据仍揭示了候选项，且正文未被输出。二次压缩要求不超过 2,800 字符，替身返回 2,866 字符，轻微违反二次目标，但仍满足原始 3,200 字符预算。

## Good Experience

前置过滤有效阻止了历史正文、重复包装和超预算首稿进入主会话。状态探测只返回短元数据，最终只回收一个带任务 ID 的最新 `agentMessage`。这次功能结果显示，主会话的研究正文负担可被约束到约 1,009 个启发式 token，而替身承担了检索、筛选与比较 10 篇论文的主要过程。

## Bad Experience

现有提取兼容性不足：若桌面结构把角色放在 item 的 `type` 字段而不是字段路径中，按路径猜角色会漏选。预算压缩也不是强保证，替身可能轻微越界，需要以确定性预算闸门判断，而不能信任提示语声明。

账户用量只以整数百分比显示，本轮从 43% 增至 45%，不能分解为替身聊天、主会话工具协调或其他同期活动的精确 token，因此不能据此证明总 token 节省。

## User Interpretation

用户希望再次测试替身对主会话 token 使用量的影响。当前结果支持“上下文隔离有效”，但仍不支持“账户总 token 必然下降”。

## Other Notes

潜在修订应让 `extract` 显式识别桌面 `userMessage` / `agentMessage` item 结构，并让预算闸门继续以实际完整载荷为准。是否修改 Portable Skill 仍需用户明确确认。
