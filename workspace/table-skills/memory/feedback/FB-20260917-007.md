# Feedback

## Skill Used

`web-task-stand-in`

## Situation

复盘替身首次回复超过提交预算后，主会话要求同一聊天再次压缩的行为。

## What Happened

接收阶段把提交时的返回预算当成硬拒收门槛，触发了第二次聊天交互。压缩回复仍轻微超过二次目标，并增加了等待、token 消耗和信息损失风险。

## Good Experience

提交时给出预算仍能有效引导替身生成紧凑答案；接收端的确定性测量也能提供实际字符、链接和启发式 token 数据。

## Bad Experience

自动要求压缩把原本可为一次提交、一次回收的任务变成多轮对话。多次摘要可能丢失证据或限定条件，而且额外消耗聊天与主会话资源。

## User Interpretation

预算应在提交时作为强输出约束；接收时只测量、标记和报告偏差，不应因普通超限自动拒收或要求二次压缩。除非结果被截断或触及宿主硬安全上限，默认保持一次提交、一次回收。

## Other Notes

桌面响应提取还应依据 `agentMessage` 或等价助手角色识别正文，而不是从字段路径猜测角色。
