# Feedback

## Skill Used

`web-task-stand-in`

## Situation

用户在 GPT／Codex 桌面应用中手动创建并明确指定 ChatGPT 会话“重任务测试”。主任务向该会话发布编号为 `WST-20260917-001` 的只读重任务：检索 10 篇 3DGS 论文并总结趋势，然后收回结论。

## What Happened

- 主任务能够定位并打开用户指定的 ChatGPT 会话。
- 首次发送接口返回会话编号，但随后的即时回读尚未显示新回合，容易被误判为未送达。
- 在先回读确认、打开目标会话并等待后，受控重试返回“聊天正在响应”，证明首次提交已经进入执行；没有继续重复发送。
- 通用等待接口无法订阅 ChatGPT 会话，只支持 Codex 任务；最终通过间隔回读 ChatGPT 会话取得完整回答。
- 回收结果包含 10 篇论文、趋势、研究缺口和精读建议，但正文混有不可直接复用的内部引用标记，且样本主要集中于 2023—2024 年，不能冒充截至 2026 年的最新前沿综述。
- 主任务对关键论文做了轻量一手来源复核，并把回收结果压缩为可采用结论。

## Good Experience

- “用户创建隔离聊天—主任务按真实会话 ID 发送—ChatGPT 独立执行—主任务回读”链路实际跑通。
- 唯一任务编号和自包含任务包足以让目标聊天独立完成重任务。
- 现有 Skill 关于不盲目重试、外部结果需核验、区分提交与完成的原则有效，避免了重复任务和过早采信。

## Bad Experience

- Skill 没有明确说明 ChatGPT 会话不能使用 Codex 任务等待接口。
- “发送返回成功但即时回读看不到”缺少专门的暂态处理规则，执行中一度难以区分延迟、未知和失败。
- 回收阶段缺少清洗规则，未提前要求去掉宿主内部引用占位符、跟踪参数或超长重复内容。
- 研究型任务没有要求区分“代表性技术脉络”与“截至检索日的最新进展”，导致答案虽然有用，但新近覆盖不足。

## User Interpretation

用户尚未提出原因判断；已要求进入下一轮讨论。当前可观察原因是桌面宿主对 Codex 任务与 ChatGPT 聊天提供了不同的等待能力，且发送、会话存储和回读之间存在可见延迟。

## Other Notes

当前证据只验证了“用户手动创建并指定既有 ChatGPT 聊天”的路线，没有验证自动创建快速对话，也没有测试 Astra 或 token 节省效果。
