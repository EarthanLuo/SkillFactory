# Feedback

## Skill Used

`web-task-stand-in`

## Situation

在前置清理内部引用占位符的修订后，再次向既有 GPT 桌面聊天提交一项检索并比较 10 篇 3DGS 编辑、生成或重光照论文的任务，并观察主会话载荷与账户用量变化。不测试 Astra。

## What Happened

任务只提交一次，最终结果只回收一次。由于桌面同步延迟，进行了两次无正文状态探测，但没有增加聊天对话轮次。回收原文 3,273 字符，前置清理后 3,251 字符、5 个普通链接、启发式估算约 1,237 token，未截断，比 3,000 字符提交目标多 251 字符。内部引用占位符数量为 0。

账户五小时窗口从 52% 增至 54%，周窗口保持 39%。这些整数百分比包含主会话协调、工具调用与可能的同期使用，不能视为替身任务的精确 token 数。

## Good Experience

一次提交、一次回收策略继续有效。最终正文包含普通链接，没有内部引用占位符；旧回合和原始会话包装未进入主会话。新增提示和前置清理形成了双层保护。

## Bad Experience

提交预算仍是软约束，本轮超出 251 字符。桌面回合列表存在约几十秒同步延迟，需要额外状态探测。账户窗口本轮上升 2 个百分点，而上一轮没有变化，进一步说明整数窗口不适合衡量单任务 token。

## User Interpretation

用户希望持续观察替身对主会话 token 使用量的影响。当前证据支持上下文载荷可稳定约束在约 1,200 个启发式 token，但账户总消耗仍无法精确归因。

## Other Notes

本轮未发现必须立即修改技能的新缺陷。状态同步探测不产生聊天轮次，且正文清理策略按预期工作。
