# Extraction

## Problem

长任务跨对话或跨 Agent 接续时，最容易丢失的不是完整聊天内容，而是影响下一步的少量事实：目标与范围、已经确认或否决的决定、关键文件版本、真实进度、授权边界和第一步验收方式。另一个问题是把“提醒”“保存材料”“创建新任务”“已成功接手”混为一个动作，导致重复创建、越权继续或把半成品当作完成。

## Approach

仓库采用一种“最小事实记录 + 分阶段核验”的交接方式：

1. 只记录恢复下一步所需的信息，不复制完整日志。
2. 对决定、进度和交接状态使用显式区分，保留“未确认”“未验证”和“结果未知”。
3. 将完整交接拆成保存、创建、只读核验、登记、授权范围内继续和接续验证。
4. 对失败和不确定回执做幂等处理：先查状态，复用已创建任务，不靠重复创建解决问题。
5. 将 Hook 限定为计数、提醒和最终文本核验辅助，不让它承担业务判断或授权。

仓库实现的具体链路进一步表明：压缩计数器只产生检查点信号，交接材料单独保存；完整交接依次经过保存／回读、创建唯一接手任务、接手方只读核验、登记真实任务编号、发送继续指令和验证首个实际动作。它还用交接编号、任务状态和“结果未知”来处理幂等与失败恢复。这个实现把“压缩后可交接”与“立即交接”分开，自动化默认只提醒，不自动新建任务。

## Reasoning

该方法可能有效，是因为它把“上下文压缩”变成“可核对的状态转移”：接手方不需要信任旧对话的叙述，而是先检查文件、版本、成果和限制；源方也不能仅凭创建回执声称已经接手。显式状态和唯一交接编号降低了重复执行风险，授权边界则把“用户同意保存”与“用户同意新建并继续”分开。

## Conditions

- 工作目录、关键成果和交接载体能够被新任务访问。
- 宿主提供可查询的任务、消息或运行状态；否则只能给出手动入口。
- 用户能够明确授权需要执行的动作范围，尤其是是否允许新建任务和继续修改。
- 任务可以被拆出一个可验证的第一步，且有实际验收依据。
- 交接记录由人或 Agent 在写入前后核对，而不是仅依赖 Hook 或模型自述。

## Hidden Assumptions

- “项目”与工作目录之间存在稳定映射，且不同任务不会同时覆盖同一交接正文。
- 关键文件版本和未提交改动不会在交接过程中被悄然替换。
- 接手任务的只读核验足以发现影响第一步的主要差异；未发现不等于没有差异。
- 用户对“继续”与“新建并继续”的语义有一致理解。
- 压缩事件、Hook 输入和任务 ID 在宿主中真实可获得；移植到其他 Agent 宿主时这些能力可能不存在。

## Transferable Experience

最值得迁移的不是具体的 Codex Hook 或命令，而是以下判断规则：

- 交接记录应服务于下一步行动，而不是成为第二份聊天全文。
- 任何状态都要带证据等级：已完成、已派发、待核验、未知应分开写。
- 变更修改权之前，先让接手方只读核验目录、版本、成果、限制和第一步。
- 不确定的创建或发送结果先查询；同一交接保持唯一接手任务。
- 自动化只做它能证明的事；业务阶段、用户是否看到提醒和是否获得授权不能由 Hook 猜测。
- 源 claims、当前用户决定和新的迁移推断要在记录中分层，避免把经验描述直接升级成规范。
- 压缩应产出一份可被交接流程直接消费的最小事实包；交接流程再负责唯一性、只读核验、授权范围和首步证据。两者是串联关系，但不应把压缩计数本身当成交接成功证据。

## Uncertainty

本次没有独立验证该仓库在真实 Windows Codex 环境中的完整运行链路，也没有验证 token 节省效果。README 明确承认网页替身的省 token 结果不理想，因此不应把“网页外包”作为已证明的优化方案。项目交接原则的可迁移性仍需在具体宿主中测试：尤其是任务状态查询、Hook 生命周期、并发写入和用户授权呈现方式。

## Possible Skill

可能启发一个“可核验的长任务交接” Skill，但目前只提出候选行为，不创建或修改 Portable Skill。若要继续，应先针对目标宿主讨论：需要保留哪些字段、哪些动作必须用户确认、什么证据才算“已接手”，以及工具不可用时的手动降级路径。之后可由用户明确选择 ADOPT、ADAPT、TEST、REJECT 或 UNRESOLVED。

## User Adaptation So Far

用户明确选择“压缩完成后直接进入交接”，不把交接再设为一次额外确认。该决定与仓库的保守默认不同，应记录为对其思路的适配：压缩完成是自动交接的触发条件；交接内部仍需保留材料校验、唯一任务、只读核验、修改权转移和异常查询等安全步骤。自动触发的具体阈值（每次压缩、达到检查点，或仅在安全位置）尚未确定。

随后用户进一步限定实现路径：先保留为不自动触发的、可手动调用且可验证的交接 Skill；待该 Skill 在实际使用中证明流程可靠，再考虑用 Hook 接入压缩事件。Hook 因而属于后续触发层，不属于第一版交接逻辑本身。
