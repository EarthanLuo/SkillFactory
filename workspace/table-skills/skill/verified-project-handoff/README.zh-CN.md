# Verified Project Handoff（可核验的项目交接）

## Skill 用途

`verified-project-handoff` 用于保存长期任务恢复所需的最小事实，创建或提供接收入口，并且只有在接收方核验交接内容后才转移后续修改权限。

这是一个手动交接 Skill，不是通用的“继续工作”机制。它不会安装、发布、删除、提交代码，也不会修改无关配置。

## 安装

通常通过 Codex 的 **Plugins Directory** 安装包含它的 `Skill Foundry` 插件。如果使用 fork 或本地 marketplace，运行 `codex plugin marketplace add <owner>/<repo>`，重启 Codex，选择对应 marketplace 并点击 **Install**。单独使用时请复制完整目录，保留 README 和 Skill 定义文件。

## 触发条件

只有在用户明确要求保存并交接、创建接收任务并继续，或明确调用本 Skill 时才使用。

普通的“继续”、上下文压缩、提醒或只读状态检查都不会触发交接。

## 交接记录应包含什么

交接记录只保留接收任务真正需要的事实：

- 目标和验收标准；
- 工作目录和版本；
- 权威文件、产物和相关引用；
- 已确认的决策、约束和授权范围；
- 与用户决策分开的 Agent 建议；
- 未解决事项和未知信息；
- 标记为“已完成”“进行中”“未开始”或“未验证”的进度；
- 下一步、前置条件和核验方法；
- 唯一交接 ID 和明确的交接状态。

不要复制完整聊天记录，也不要把凭据写入交接记录。

## 核验流程

1. 写入前先读取现有状态载体，并合并并发修改。
2. 优先增量更新项目现有状态文件；没有时才在项目根目录使用 `PROJECT_STATE.md`。
3. 回读文件，确认路径、引用、决策、约束和下一步正确。
4. 有创建任务能力时只创建一个接收任务；否则提供可复制的手动开场消息和产物路径。
5. 要求接收方只读核验目录、交接 ID、关键产物、约束和第一步。
6. 只有在接收方确认这些事实且没有阻塞差异后，才转移写入权限。
7. 核验第一个实际动作或任务状态。出现未知情况时，保留准确状态和手动入口。

## 状态词汇

必须区分以下状态：

```text
材料已核对
等待接收方核验
准备继续
已完成交接
受阻
```

“已创建”或“已派发”不等于“已完成交接”。接收方只回复“准备开始”也不足以证明已经完成核验。

## 硬性边界

- 一次明确调用只覆盖用户授权的交接动作。
- 回执不明确时不要重复创建接收任务。
- 不要让源任务和接收任务并行修改同一批业务文件。
- 在接收方核验目录、ID、产物、约束和第一步之前，不要声称交接成功。
- 工具、权限或核验步骤不可用时，应降级为准确的手动入口，不要猜测成功。

## 可移植性

这是一个自包含 Skill。复制或安装时，应保留 `SKILL.md`、本 README 和 `README.zh-CN.md`。Skill 不得依赖项目的 `memory/` 目录或其他 Skill。
